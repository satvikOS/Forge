To understand the unified UI/UX architecture of enterprise CAD platforms, it helps to look at them not as drawing applications, but as visual databases. Platforms like Siemens NX, Dassault Systèmes (CATIA), and PTC Creo share a foundational user experience blueprint designed to handle massive amounts of geometric and parametric data.

To see exactly how these interfaces operate in real-world engineering workflows, consider this unified walkthrough of a standard engineering task: creating a custom mounting bracket inside a complex machine assembly.

---

1\. The Screen Layout (The Workspace Anatomy)

When an engineer opens the software, the screen is strictly divided into four zones designed to maximize screen real estate and reduce eye movement.

* The Canvas (The Central Viewport): This is a high-performance 3D graphics zone. The background is a dark matte gray to minimize eye strain during 10-hour shifts. The mounting bracket sits in the center, surrounded by the rest of the engine assembly, which is faded or made semi-transparent to provide spatial context without cluttering the screen.  
* The Left Sidebar (The Feature/Model Tree): This is the chronological "DNA" of the part. It lists every single 3D operation in order: *Sketch 1 \-\> Extrusion 1 \-\> Hole 1 \-\> Fillet 1*.  
* The Top Area (The Ribbon & Command Bar): A dense row of tool tabs (Sketch, Surface, Assembly, Sheet Metal). Clicking a tab reveals dozens of precise technical icons.  
* The Bottom Bar (The Status & Snapping Center): A thin strip displaying the exact X, Y, Z coordinates of the mouse cursor and toggles for "Snapping" (forcing the cursor to lock onto exact midpoints, centers, or intersections).

---

2\. Step-by-Step UX Workflow Example: Designing the Bracket

Phase A: Entering the Sketch Sandbox (Modal States)

The engineer clicks the Sketch icon on the top ribbon. The UI immediately changes states, known as a Modal Workflow.

1. The Interface Locks Down: Non-essential 3D tools gray out. The software is now waiting for one specific input: *Where do you want to draw?*  
2. Visual Prompting: In the viewport, the X, Y, and Z planes light up in bright orange and green.  
3. The View Shifts: The engineer clicks the top horizontal plane. The 3D viewport smoothly spins and flattens into a perfect 2D bird's-eye view.

Phase B: Drawing and Geometric Constraints (Visual Feedback)

The engineer draws a rough rectangle with the mouse. In a consumer app like Figma, this rectangle is just free-floating pixels. In CAD, it requires mathematical logic.

1. The Dimension Engine: The moment the rectangle is drawn, the software automatically generates faint, light-blue "Weak Dimensions" showing temporary measurements.  
2. Adding Constraints: The engineer clicks the left line and the right line, then selects the Parallel constraint from a floating menu. Small geometric symbols (like tiny parallel lines \=) appear next to the sketch lines.  
3. The Color-Coded Truth: The lines turn from Blue (Under-constrained/loose) to Black (Fully-constrained/locked). This color shift tells the UX user that the rectangle is mathematically locked in space and cannot accidentally warp.

Phase C: Baking the 3D Geometry (The Dashboard Interface)

The engineer clicks "Exit Sketch" and hits the Extrude tool to turn the 2D rectangle into a solid 3D block.

1. The Contextual Dashboard Opens: A dedicated panel slide-outs right next to the cursor (NX) or at the top of the screen (Creo). It demands specific values: *How thick? In which direction? Is it cutting through another part or adding to it?*  
2. Real-Time Preview: As the engineer types 25mm, a ghosted, semi-transparent 3D volume previews the thickness in the viewport before committing.  
3. The Tree Updates: The engineer clicks the green checkmark. The dialog disappears, the viewport returns to normal, and a new item labeled Extrusion\_1 instantly populates at the bottom of the left-hand Feature Tree.

Phase D: Modification via "Time Travel" (History Rollback)

Later, the engineer realizes the mounting bracket needs to be wider to clear a pipe in the engine. Instead of redrawing it, they use the ultimate CAD UX feature: The Rollback Bar.

1. Traveling Backwards: The engineer goes to the left-hand Feature Tree, clicks a horizontal bar at the bottom, and drags it *up* past the Extrusion\_1 step.  
2. Visual Regression: The 3D solid bracket instantly vanishes from the screen, reverting the viewport back to the original 2D wireframe sketch.  
3. The Ripple Effect: The engineer double-clicks the width dimension, changes 100mm to 150mm, and pushes the Rollback Bar back down to the bottom of the tree. The software recalculates the geometry, and the solid 3D bracket reappears, perfectly updated without breaking any subsequent holes or fillets.

---

3\. The Power User UX: Eliminating Mouse Travel

To an outside observer, an expert using NX, CATIA, or Creo looks like they are playing a fast-paced video game. This is because the UI is optimized to eliminate mouse travel. Moving the mouse from the center of a 4K monitor to the top ribbon to click a button takes too much time.

* Radial Pop-ups: Right-clicking anywhere on the 3D part spawns a circular "pie menu" directly under the cursor. Moving the mouse a mere 5 pixels to the upper-right slice activates the "Chamfer" tool instantly.  
* Keyboard Chaining: Left hands stay mapped to the keyboard. Typing C might launch the circle tool, while E launches extrude. The graphical interface effectively becomes secondary to muscle memory.

# **Archie: From Benchmark-Leading CAD Model to a Physical Engineering Platform**

## **Strategic objective**

Archie should no longer be developed primarily as a model that produces better-looking CAD geometry.

It should become an **autonomous physical-engineering system that converts incomplete engineering intent into verified, editable, manufacturable product definitions**.

Today, Archie demonstrates a strong foundation:

* engineering-drawing interpretation;  
* native B-Rep construction through OCCT;  
* STEP generation;  
* targeted CAD editing;  
* geometric validity;  
* benchmark-leading performance.

The next level is substantially harder. Archie must determine whether a design:

* represents the intended engineering function;  
* can be edited without destroying design intent;  
* can be manufactured using available processes;  
* satisfies tolerances and interface requirements;  
* survives relevant physical loads;  
* assembles with adjacent components;  
* can be inspected;  
* performs correctly after fabrication.

The long-term north-star metric should therefore be:

**The percentage of unseen engineering requirements that Archie converts into shop-ready manufacturing packages that pass first-article inspection without manual CAD repair.**

A leaderboard score remains useful, but physical-world acceptance becomes the actual measure of success.

# **What Archie should learn from Kyrall**

Kyrall represents an important direction for AI-native CAD products. It generates editable, parametric models from text, sketches, meshes, engineering specifications, requirements, and sizing results. Its product also emphasizes manufacturable output, conversational refinement, exports, an API, and a Context Manager that grounds generations in company files, design rules, constraints, and standards.

The strongest elements for Archie to adopt are:

## **1\. A persistent engineering context layer**

Kyrall’s Context Manager is strategically important because professional design rarely begins with one isolated prompt. Engineering decisions are grounded in:

* internal design standards;  
* prior products;  
* component libraries;  
* supplier catalogs;  
* manufacturing capabilities;  
* approved materials;  
* preferred tolerances;  
* calculation reports;  
* sizing spreadsheets;  
* test results;  
* field failures;  
* company-specific conventions.

Archie needs an equivalent **Engineering Context Vault**, but it should go further by connecting every generated feature to the source requirement, standard, calculation, drawing annotation, or prior design that caused it to exist.

Every generated result should be traceable:

Feature: mounting\_bore\_04  
Source: drawing view B  
Dimension: Ø10.2 mm  
Tolerance: \+0.10 / 0.00  
Standard: internal fastening rule FS-14  
Manufacturing process: drilling  
Verification status: passed  
Confidence: 0.98

That creates auditability rather than merely additional prompt context.

## **2\. Conversational parametric refinement**

Kyrall allows users to modify dimensions and refine generated components. Archie should support the same interaction, but edits must operate on persistent semantic features rather than approximate geometric regions.

A user should be able to say:

Increase the four mounting bores to 12 mm, preserve their bolt-circle diameter, and leave every other feature unchanged.

Archie should then:

1. identify the semantic hole pattern;  
2. resolve the correct parameters;  
3. modify only the intended dimensions;  
4. rebuild the feature tree;  
5. compare before-and-after geometry;  
6. prove that non-target geometry remained unchanged;  
7. rerun manufacturability and validity checks;  
8. provide an edit report.

## **3\. API-first deployment**

Kyrall exposes an API for teams building on top of its system. Archie should also be designed as an engineering platform rather than only a standalone interface.

The same Archie engine should support:

* a web application;  
* CAD plug-ins;  
* PLM and PDM integrations;  
* manufacturing portals;  
* robotics-design pipelines;  
* internal enterprise tools;  
* benchmark runners;  
* automated engineering agents;  
* batch drawing conversion;  
* custom vertical applications.

## **4\. Multiple usable export formats**

Archie should produce more than a STEP file. Kyrall already emphasizes standard geometry exports such as STEP, STL, GLB, and related formats.

Archie’s production package should include:

* native parametric model;

4. modify the smallest possible parameter or operation;  
5. rebuild affected dependencies;  
6. rerun all relevant gates;  
7. record the complete repair trace.

This is the difference between stochastic generation and engineering automation.

# **ADDENDUM (2026-07-16) — Forge desktop app must be PURE C++**

The entire Forge desktop application must be built on a **pure C++ framework** — on
**all three platforms: Windows, Linux, and macOS**. Forge renders complex 3D
engineering graphics (large assemblies, dense B-Rep, live FEA/CFD visualization) and
requires **maximum performance with extremely low latency — no lag, no stutter**.

Requirements:

- **No Electron / Node / web-frontend runtime.** The app is a native C++ executable per
  platform. This removes the JavaScript/Chromium/Node-API bridge entirely.
- **Direct in-process linkage to the native OCCT (and unified CGAL/Manifold/libfive/
  PicoGK) C++ kernel** — no `.node` addon boundary, no serialization across a bridge;
  geometry and rendering share memory.
- **Native GPU rendering** at the lowest practical level for each OS — Metal on macOS,
  Direct3D 12 on Windows, Vulkan on Linux (or Vulkan cross-platform via MoltenVK on
  macOS) — targeting sustained high frame rates on massive scenes with sub-frame input
  latency.
- **A C++ UI framework** (e.g. Qt — the professional-CAD standard used by NX/Fusion/
  FreeCAD — and/or an immediate-mode layer such as Dear ImGui), delivering the enterprise
  NX/CATIA/Creo UI/UX blueprint above natively.
- **Single shared C++ codebase** across the three platforms; platform code isolated to
  thin backends (windowing, GPU device, file dialogs).
- **Still driven by Archie via CUA** — the model operates the native GUI like a human
  (computer-use works on any native window), so the pure-C++ move does not change the
  Archie-drives-Forge principle; e2e verification adapts to native-GUI automation.
- **The interface is REIMPLEMENTED as Forge's own IP — modern, not a clone.** The C++
  framework is only the foundation. Do NOT ship stock Qt widgets, nor a copy of the dated
  NX/CATIA/Creo chrome. Build Forge's own bespoke, contemporary design language — custom
  controls and a distinctive modern UI system — that *expresses the enterprise UX
  principles* (feature-tree DNA, modal sketch sandbox, rollback/time-travel bar, radial
  pie menus, keyboard chaining, 4-zone workspace) as proprietary Forge intellectual
  property, not a lookalike of any existing CAD tool.

This supersedes the Electron/React/Vite desktop stack. Peak technology, industrial grade,
no lite version.
