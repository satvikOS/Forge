 0.9 Assemblies and hierarchy
 Large assemblies remain hierarchical. The system must not flatten a million fasteners into one unmanageable
 linear list, nor hide them behind a count with no identities.

  • A part definition has one versioned feature DAG.
  • An occurrence references that definition by immutable revision/hash and supplies configuration, transform,
     quantity role, and instance metadata.

  • A subassembly owns its occurrence and mate graph.
  • Repeated components use typed occurrence patterns with explicit instance IDs.
  • Standard purchased components may remain referenced library parts; their internal manufacturing tree need
     not be copied unless the user intends to manufacture or modify them.

  • Flexible components and alternate-position representations have explicit state models.
  • Suppression, configuration, and effectivity expressions are deterministic and evaluable.
 The count report distinguishes unique definitions from occurrences. A BOM quantity must reconcile with
 occurrence state and the product structure.

  • location in a named coordinate frame;
  • persistent lineage through split and merge events;

 Before emission, Archie provides a forecast by node family and confidence range. The forecast is for scheduling

 large forecast may trigger staged delivery or ask the user to select product scope, but accepted scope cannot be
 silently discarded.

 Forecast errors are tracked. Systematic underestimation is a planning defect because it causes context and
 latency failures; systematic overestimation may signal needless feature inflation.

 1. The governing product axiom
     A user gives Archie an engineering request in text, images, video, sketches, drawings, PDFs, existing CAD,
     or a combination. Archie turns that evidence into a complete, explicit, versioned engineering specification;
     reasons over competing interpretations; asks only questions that materially change the result; emits an
     exact and replayable native C++ feature DAG of whatever length the job requires; Forge compiles it into
     geometry; deterministic validators prove or reject the result; and the user receives editable CAD plus the
     evidence needed to trust, revise, manufacture, inspect, or simulate it.

 In compact form:

   Evidence -> Specification -> Candidate intent -> Exact feature DAG
             -> Deterministic compilation -> Verification/repair -> Deliverables


 The feature DAG is the executable design record. The B-rep is a compiled artifact. A render is an observation.
 None may substitute for another.




 2. Non-negotiable laws
 1. The shipped first-party runtime is native C++. Inference, orchestration semantics, the feature IR,
      compiler, kernel integration, validation, persistence, UI, and audit logging execute in C++. Offline training
      and data preparation may use Python because forcing the training ecosystem into C++ would delay the
      product without making the shipped product more native.

 2. SearXNG is the only production network tool. A self-hosted SearXNG sidecar runs on the same Mac and
      the C++ runtime calls its documented local HTTP search API. SearXNG may retrieve public web references
      only after explicit tool invocation and query redaction. Its implementation does not enter the Forge process,
      and it cannot supply compute, model inference, geometry, simulation, storage, or executable instructions.

 3. Reasoning may be probabilistic; committed output is deterministic. Archie may explore multiple
      candidate interpretations, decompositions, and repair strategies. The selected specification, canonical
      feature DAG, compiler behavior, and acceptance result are deterministic under a pinned build and input
      bundle.

 4. The executable feature tree is exact and elastic. Its length is a consequence of complete design intent,
      not a token budget, example length, or UI preference. It may be 10×, 100×, or orders of magnitude longer
      than a preliminary plan. It must never be shortened by replacing required operations with vague prose.

 5. No silent truncation. If context, time, memory, or compute is exhausted, Archie checkpoints the graph and
      returns PAUSED_INCOMPLETE. It must not claim success, invent a compact substitute, or discard generated
      work.

 6. No benchmark memorization. Public evaluation inputs, private ground truth obtained improperly, known
      answers, and submission artifacts are excluded from training and retrieval. Benchmark optimization means
      learning transferable construction and editing competence, not answer-key contamination.

 5.2 Production inference

 Exploration mode

  • fixed model package and prompt template;
  • deterministic or lowest-variance supported sampler;
  • fixed seed where the runtime honors it;
  • schema-constrained output;
  • canonical units, numeric representation, ordering, and serialization;
  • no unresolved identifiers or free-form executable prose;

 8. Engineering Specification Graph
 The ESG is the complete semantic contract before geometry. It prevents a visually plausible model from quietly
 violating the request.


 8.1 Required entity families
  • requirements, subrequirements, priorities, and acceptance criteria;
  • functions, flows, loads, operating states, and failure conditions;

  • materials, treatments, finishes, colors, and prohibited substances;
  • manufacturing processes, tooling directions, stock constraints, and inspection plans;
  • interfaces, keep-outs, envelopes, connectors, fasteners, and service clearances;
  • parts, bodies, assemblies, configurations, variants, and quantities;

 8.2 Traceability

 predicates. Every feature node maps back to a requirement, construction necessity, or verified reusable library

 latitude.

 The minimum traceability chain is:

   SourceEvidence -> ESG requirement/decision -> FeatureId(s)
                    -> compiled topology/body -> verification result -> deliverable


 The release gate is 100% mapping coverage for in-scope requirements. "Not applicable," "deferred," and
 "requires human approval" are explicit states, never missing rows.


 8.3 Requirement conflict policy
 When requirements conflict, Archie must not optimize silently. It produces the smallest conflict set, explains the
 physical or logical incompatibility, and offers ranked resolutions. User priority wins unless it creates an
 unapproved safety, legal, or impossibility condition.

 9. Native C++ feature IR and compiler
 9.1 IR design principles
 The feature IR is a typed engineering language, not arbitrary C++ source pasted into the application. It must be
 easy for a model to emit, strict for a compiler to reject, safe to migrate, and stable enough for decades of project
 history.

  • Closed executable vocabulary: feature kinds are registered, versioned types. Unknown kinds are rejected.
  • Canonical representation: normalized UTF-8 identifiers, canonical SI values, fixed ordering, finite numeric
     values, and deterministic floating serialization.

  • Explicit schemas: no executable std::any, untyped property bags, arbitrary shell commands, or embedded
     scripts.

  • Separate definition and evaluation: the serialized graph describes intent; trusted C++ code performs the
     operation.

  • Schema evolution: migrations are explicit, reversible when possible, and validated against golden projects.
  • Content addressability: immutable node payloads, chunks, library components, and evidence use hashes.
  • No raw topology indices: stable queries and lineage tokens select geometry.
  • No hidden global state: tolerances, units, coordinate frames, materials, kernel settings, and configurations
     are project or node inputs.

  • Fail-closed parsing: duplicate IDs, unknown fields where prohibited, overflow, NaN, infinity, cyclic
     dependencies, and unresolved references stop compilation.

  • resource and latency cost after correctness.
 Compiler failure diagnostics are structured feedback, not a reason to reward superficial shape matching. Reward
 hacking tests include no-op padding, hidden bodies, invalid suppression, tolerance inflation, screenshot gaming,
 and benchmark-specific branching.

 Stage E - quantization-aware validation
 Evaluate Q4, Q5, Q6, and any mixed quantization candidates on the same hidden suite. The smallest package
 that passes accuracy, calibration, long-graph, and latency gates wins. Do not assume a quantization is
 acceptable from perplexity alone.

 Stage F - champion/challenger promotion
 The incumbent remains production until the challenger passes statistical and engineering significance
 thresholds, regression limits, safety tests, memory/latency budget, and reproducibility. Promotion produces a
 signed model card and rollback package.


 15.3 Dataset record and sampling
 Every training sample carries:

  • source dataset and original artifact hash;
  • source-use and permitted-purpose decision;
  • generator/human/tool provenance;
  • part family, operation families, domain, difficulty, and representation;
  • quality and verification results;
  • contamination split/group identifiers;
  • private/public status and deletion lineage;
  • transformations, augmentations, and synthetic ancestry;
  • sample weight and curriculum stage.
 Split by design family, source project, geometry lineage, and near-duplicate cluster-not random rows. Near
 duplicates across train/test are contamination even when filenames differ.

 15.7 Adapter strategy
  • one stable base model package;
  • a small number of composable, versioned domain adapters only when evaluation proves benefit;
  • no adapter stack with unknown interaction effects;
  • routing policy included in the signed package;
  • adapter merge/quantization tested as a unique model;
  • full rollback to base and previous champion;
  • on-device inference only;
  • any separately invoked training or adapter preparation is a development process, never a runtime service or
       fallback, and installed Archie remains complete when every network interface except the SearXNG browser
       path is denied.

      behavior, cancellation latency, checkpoint size, and storage growth.

 silent performance modes. They are distinct analysis methods with explicit validity envelopes and cannot inherit
 acceptance from a higher-fidelity method.

 cover small parts, drawing reconstruction, long feature graphs, assemblies, and concurrent geometry/rendering.

 21.3.3 Cleanup protocol
 1. forge-storage scan computes capacity, free-space headroom, class totals, age, reference graph, active
      process handles, Git/worktree state, leases, and candidates.

 2. forge-storage plan emits a deterministic dry-run manifest with exact canonical paths, bytes, reason, proof
      checks, recovery method, and exclusions.

 3. Cheap disposable caches may be deleted immediately after path, reference, and active-handle validation.
 4. Valuable or expensive candidates move atomically to a Forge quarantine on the same volume, preserving
      their manifest and original path. The default grace period is configurable and never silently shortened by disk
      pressure.

 5. Before purge, Forge repeats every eligibility check. A new reference, dirty state, lease, failed archive
      verification, or ambiguity returns the artifact to KEEP.

 6. Purge uses exact manifest entries, never recursive wildcards. Each action appends a tamper-evident receipt
      containing path hash, content/manifest hash, bytes, reason, policy, timestamps, and recovery status.

 7. Cleanup is crash-safe and idempotent. A crash cannot leave the registry claiming data is present when it is
      absent.

 Worktree cleanup additionally runs repository-aware checks: enumerate with Git, enter the exact worktree, verify

 integration/remote preservation point, verify no Claude task/session owns it, remove the worktree through Git,
 then prune only stale administrative records. A directory named "worktree" is never enough evidence.

 21.3.4 Storage pressure and scheduling
 The user configures a minimum free-space target as both a percentage and absolute byte floor. Defaults are
 derived from measured volume size and workload, then shown for approval. Status bands are HEALTHY, WATCH,
 PRESSURE, and CRITICAL.

  • WATCH: stop speculative cache growth and present the dry-run reclaim plan;
  • PRESSURE: pause new large downloads/builds/training imports, purge safe disposable caches, quarantine
     proved candidates, and resume only when projected peak fits with headroom;

  • CRITICAL: stop state-expanding jobs at safe checkpoints; preserve projects, manifests, databases,
     current/rollback packages, and audit records; perform only pre-authorized exact cleanup;

  • no pressure state permits deleting uncertain, dirty, unique, user-authored, or pinned data.
 The storage governor runs at application startup in scan-only mode, before any operation with a declared large
 footprint, after dependency/model/dataset activation, after agent-team integration waves, after completed
 import/training/evaluation pipelines, and on a configurable low-priority schedule. It reports current use, projected
 peak, reclaimable bytes by confidence, quarantined bytes and deadlines, and the largest blockers.
